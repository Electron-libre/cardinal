# Cardinal synchronisation

## Intent

A project keeps Cardinal, the shared agent harness (skills, hooks, scripts), in step with the central repository
without merging by hand, and learns at once when a managed file drifted from it.

## Requirements

- **SYN-1** (deterministic) `sync` must copy every file under the source's `files/` to the same relative path of the project, executable bit included, and `check` must report a changed executable bit as a modification.
- **SYN-2** (deterministic) `sync` must overwrite a managed file that was not modified locally since the last sync when the source changed.
- **SYN-3** (deterministic) `sync` must not overwrite a managed file modified locally, must report it as a conflict and must fail, unless `--force` is given.
- **SYN-4** (deterministic) `sync` must copy a file under the source's `seed/` only when the project does not have it yet, and must never touch it afterwards, except the managed entries of `.claude/settings.json` (SYN-29).
- **SYN-5** (deterministic) `sync` must delete a managed file the source dropped when it was not modified locally, and must keep it, no longer managed, when it was.
- **SYN-6** (deterministic) `sync` must be idempotent: a second run reports nothing and leaves the project byte-identical.
- **SYN-7** (deterministic) `sync --dry-run` must report what it would do and must not write anything, lock included.
- **SYN-8** (deterministic) `check` must list every managed file modified or deleted since the last sync, and nothing else.
- **SYN-9** (deterministic) `init` must create the project's configuration, `.claude/cardinal.toml` with the table `[cardinal]`, holding the source and the project-owned defaults of the source's `seed/.claude/cardinal.toml`, and must refuse to overwrite an existing one.
- **SYN-10** (deterministic) `sync` and `check` must fail without deleting anything when the source has no `files/` directory, or when the lock cannot be read or names a path outside the project.

- **SYN-11** (deterministic) `update` must resolve the requested revision (a branch, a tag or a commit; the head of the source's default branch when none is given) to a full commit hash, write that hash to `rev` in the table of the configuration (`[cardinal]` of `.claude/cardinal.toml`) with the requested name in a trailing comment, then run the `sync` against it.
- **SYN-12** (deterministic) `update` must change only the `rev` line of the configuration: every other line and comment stays byte-identical, and a missing `rev` is inserted right after `source`. When the file cannot be edited that way (a quoted or dotted key), `update` must fail changing nothing.
- **SYN-13** (deterministic) `update` must leave the project untouched, configuration and lock included, when the `sync` would report a conflict (unless `--force` is given), when the revision is unknown or when the source cannot be read.
- **SYN-14** (deterministic) `update` must fail, changing nothing, when the source is a local directory, since it has no revision.
- **SYN-15** (deterministic) `update --dry-run` must report the target revision and what the `sync` would do, and must write nothing.
- **SYN-16** (deterministic) `update` must report the previous revision (or that there was none), the new one and the files changed.
- **SYN-17** (deterministic) When `rev` is a full commit hash that no branch or tag of the source points to any more, `sync` and `update` must try to fetch that commit by its hash, and use it when the source serves it. When the source does not, they must fail changing nothing, with an error that names the pinned commit as gone from the source and says to run `cardinal update`.
- **SYN-18** (deterministic) `sync` (so `init` followed by `sync`; `init` alone only writes the configuration, the hook is not there yet) must install the native review gate in the hooks directory of the project's git repository: an executable `pre-commit` script that starts with a mark line and runs from the work tree `rust-script .claude/hooks/require_code_review.rs native` when that file and `rust-script` are there (a work tree of an older revision), else `cardinal run review-gate native` (BIN-9), failing the commit with that exit code; when the launcher cannot run the tool (exit 3, BIN-14), when the work tree has neither the hook script nor `.claude/cardinal.toml`, or when the program it needs is not on the path, the script must warn on stderr and let the commit through.
- **SYN-19** (deterministic) When a `pre-commit` without the mark already exists, the installation must move it to `pre-commit.user` and the installed hook must run it after the review gate, passing its arguments and failing the commit when it fails; it must never overwrite the user's hook, and must fail changing nothing when a `pre-commit.user` already exists, unless it is the same file as that `pre-commit` (a hard link of it, which a `sync` killed during the move leaves behind): then it must install the gate over `pre-commit` and keep `pre-commit.user`.
- **SYN-20** (deterministic) `sync` must reinstall the native gate when it is missing, no longer executable or different from the managed one, and report nothing when it is up to date (idempotent, as SYN-6); `--dry-run` must report the installation and write nothing.
- **SYN-21** (deterministic) For a linked worktree, or a project whose `.git` is a file, the gate must be installed in the `hooks` directory of the common git directory.
- **SYN-22** (deterministic) When `core.hooksPath` is set for the project, `sync` must install nothing, report that the native gate is not installed and why, and succeed; a project that is not a git repository, or whose source manages no hook running `cardinal run review-gate` (SYN-29) and has no `.claude/hooks/require_code_review.rs` among its files (an older revision), gets no gate and no error (SYN-60 removes one installed before).
- **SYN-23** (deterministic) `check` must report `missing: native review gate` when the project is a git repository whose lock records a managed hook running `cardinal run review-gate` (even removed from the settings since) or the managed file `.claude/hooks/require_code_review.rs` (an older revision, even deleted since), whose hooks directory lacks the managed gate and where `core.hooksPath` is unset, and `modified: native review gate` when it differs, but `conflict: native review gate (<hooks>/pre-commit and <hooks>/pre-commit.user both exist: merge them by hand into <hooks>/pre-commit.user (replace it if it is a dangling link), remove <hooks>/pre-commit, then run `cardinal sync`, which never overwrites a hook of yours)` when that `pre-commit` is not the gate and a `pre-commit.user` exists too, a dangling link included, that is not the same file as that `pre-commit` (`<hooks>` is the hooks directory of SYN-21; `sync` refuses to install the gate then, SYN-19, with the text between the parentheses as its error); it must not report it otherwise, nor when the `CI` environment variable is set (a fresh clone of a CI run has no git hooks and nobody commits there).
- **SYN-24** (deterministic) `check` must print `warning: .claude/settings.json lacks the deny rule <rule>` for each rule of REV-19 (`specs/review-gate.md`) that the `permissions.deny` list of the project's `.claude/settings.json` lacks, when the lock records the review gate as SYN-23 says and that settings file exists; the warning goes to stderr and must not make `check` fail. `sync` adds the rules the source manages (SYN-29); this is how a project whose rule was removed by hand, or whose source does not manage it, learns of it.
- **SYN-25** (deterministic) `check` must print `warning: .claude/settings.json runs the missing hook <path>` for each hook command of the `hooks` table of the project's `.claude/settings.json` that names a file under `.claude/hooks/` the project does not have, when that settings file exists; the warning goes to stderr and must not make `check` fail. A hook the source dropped is deleted by `sync` (SYN-5), but the seeded settings keep running it.
- **SYN-26** (deterministic) `check` must print `warning: .claude/settings.json does not turn off the attribution` when the project's `.claude/settings.json` exists and its `attribution` is neither `false` nor an object whose `commit` and `pr` are both empty strings; the warning goes to stderr and must not make `check` fail.
- **SYN-27** (deterministic) `sync` and `update` must print the warnings of SYN-24 to SYN-26 to stderr, once, judged on the project as the sync leaves it, and must not fail because of them: a hook the sync removed is missing, one it added is present. Under `--dry-run` they must judge the project as the sync would leave it, writing nothing. The deleting `sync` is how a project loses a hook its settings still run (SYN-5): it must say so at once, not at the next `check`.
- **SYN-28** (deterministic) `check`, `sync` and `update` must print `warning: the transcripts are deleted after <n> days (cleanupPeriodDays); set it to at least 365 in <user settings>` when the `cleanupPeriodDays` of the user settings (`settings.json` in `CLAUDE_CONFIG_DIR`, or else in `~/.claude`) is missing, not a number or below 365 (`<n>` is 30, the default, when it is missing or not a number), and `warning: <file> sets cleanupPeriodDays to <n> days, below 365` for each of the project's `.claude/settings.json` and `.claude/settings.local.json` that sets a number below 365; the warning goes to stderr, comes out once, must not make them fail, and is not printed when the `CI` environment variable is set. Claude Code deletes the transcripts of every project after this period, with the value of whichever session sweeps: the evaluation of Cardinal reads them over several revisions.
- **SYN-29** (deterministic) When the source has `entries/.claude/settings.json`, `sync` must add to the project's `.claude/settings.json` each managed entry it lacks: each string of the fragment's `permissions.allow`, of its `permissions.ask` and of its `permissions.deny`, appended to the project's list of the same name, and each hook object of the fragment's `hooks` table, appended to the `hooks` of the first group of the same event with the same `matcher` (none, `""` and `"*"` counting as one value, since each matches every tool), or else to a new group appended to the event; the keys that are missing are created.
- **SYN-30** (deterministic) The lock must record each managed entry of the source as `sync` leaves it, so that `check` and the next `sync` know which entries of the settings are Cardinal's.
- **SYN-31** (deterministic) `sync` must remove from the project's settings each entry the lock recorded that the source no longer manages, when the settings still hold it unchanged (JSON equality, key order ignored); a group left with no hook is removed, and so is an event left with no group. A hook whose command or options changed in the source is the removal of the old entry and the addition of the new one, which takes the place of the old one when the settings hold it; a dropped entry the settings no longer hold unchanged is reported as kept, once.
- **SYN-32** (deterministic) `sync` must leave every other key, value and entry of the settings as the project wrote it, key order included, and must not write the file when it adds and removes nothing (SYN-6); when it writes it, the file is JSON indented by two spaces, one key or element per line, ending with a newline.
- **SYN-33** (deterministic) An entry the lock recorded that the settings no longer hold unchanged (removed or edited by the project) and that the source still manages must be reported as a conflict on `.claude/settings.json <entry>` and make `sync` fail like a conflicting file (SYN-3), the entry not added back, unless `--force` is given, which adds it back.
- **SYN-34** (deterministic) `sync` must print each entry it adds or removes as `<outcome>: .claude/settings.json <entry>` (`<entry>` is `allow <rule>`, `ask <rule>`, `deny <rule>` or `hook <event> <matcher> <command>`, the matcher left out when the group has none), and `--dry-run` must print the same lines and write nothing.
- **SYN-35** (deterministic) When the project's `.claude/settings.json` is missing (once the seeds are copied), cannot be read, is not valid JSON or does not have the shape of SYN-29, `sync` must not touch it, must keep the entries the lock recorded and must not fail because of it; a warning on stderr says why when the file exists.
- **SYN-36** (deterministic) `check` must print `missing: .claude/settings.json <entry>` for each entry the lock recorded that the settings no longer hold unchanged, and nothing for the other entries of the settings, nor when the settings are missing, cannot be read, are not valid JSON or are not in the shape of SYN-29.
- **SYN-37** (deterministic) When `init`, `sync`, `update` or `check` fails with an error (not a conflict nor a drift, which exit 1), `cardinal` must print the error on stderr and exit 3, a code Claude Code does not read as a refusal (it blocks on 2, BIN-14), so that a hook running one of them never blocks the agent.
- **SYN-38** (deterministic) `check`, `sync` and `update` must print `warning: the fixed context is <total> bytes, over the budget of <budget> (fixed_context_budget in <config>); the largest part is <part> (<bytes> bytes)` to stderr, once, when the `fixed_context_budget` of the `[project]` table of the configuration (`.claude/cardinal.toml`) is a whole number and the fixed context of the project's work tree exceeds it, and must not fail because of it; `<config>` is the path of that configuration; `<total>` is the sum of the bytes REP-2 counts in a tree, `claude_md_bytes`, `agents_md_bytes` and the skill description bytes, counted in the project's work tree (`CLAUDE.local.md`, personal and kept out of git, counted in neither); `<part>` is `CLAUDE.md` (the `claude_md_bytes`), `AGENTS.md` or `skill descriptions`, the first of these in that order on a tie. `sync` and `update` judge the work tree as they leave it, and under `--dry-run` as it is.
- **SYN-39** (deterministic) `check`, `sync` and `update` must print `warning: fixed_context_budget in <config> is not a whole number of bytes` (`<config>` as SYN-38) to stderr, once, when the key is present with another value than a whole number from 0 up, and must not fail because of it; without the key, nothing about the budget is printed.
- **SYN-40** (deterministic) When the file `cardinal-format` at the root of the source holds a whole number greater than the format the running `cardinal` reads, `sync` and `update` must fail with the error `<source> needs a cardinal that reads the format <n>, this one reads up to <m>: install it with `<command>`` (exit 3, SYN-37) and write nothing, `--dry-run` included; `<command>` installs the `cardinal` of the revision synced, the commit checked out for a git source (BIN-20 for its form). A source without the file has the format 1; a file that holds no whole number is an error that names it.
- **SYN-41** (deterministic) The lock must record the format of the source it was synced from (SYN-40), as a line `format <n>` before every other line but the comments (one space, so that a `cardinal` older than this requirement skips it); a lock without the line has the format 1.
- **SYN-42** (deterministic) When the lock records a format greater than the one the running `cardinal` reads, wherever the line stands, `check`, `sync` and `update` must fail with the error `<lock> was synced from a source of the format <n>, this one reads up to <m>: install it with `<command>`` (exit 3) and write nothing, before any other line of the lock is judged; `<command>` installs the `cardinal` of the `rev` of the configuration (`.claude/cardinal.toml`).
- **SYN-43** (deterministic) The format a `cardinal` reads must be the one the `cardinal-format` of its own revision declares.
- **SYN-44** (deterministic) withdrawn: the project files carry the new names whatever the source, and a source below the format 3 is refused (SYN-51, ADR 0016).
- **SYN-45** (deterministic) withdrawn: every consumer is migrated to the new names, no project of the old names is left to move (ADR 0016).
- **SYN-46** (deterministic) withdrawn: `init` writes the new names only (SYN-9, SYN-51).
- **SYN-47** (deterministic) withdrawn: `check`, `run`, the tools and the native gate read `.claude/cardinal.toml` and `.claude/cardinal.lock` only; the readers of the history keep both names (ADR 0016).
- **SYN-48** (deterministic) withdrawn: every source below the format 3 is refused (SYN-51).
- **SYN-49** (deterministic) `init`, `sync`, `update`, `cardinal run` and the launcher must treat the source as a git repository to clone when it contains `://`, starts with `git@` or ends with `.git` (case sensitive, nothing after it), and as a local directory read in place otherwise.
- **SYN-50** (deterministic) A git source of SYN-49 that is a path (it contains no `://` and no `:` before its first `/`, which git reads as `host:path`) must be resolved against the project root, its symlinks resolved, into an absolute `file://` URL, its `.` and `..` components removed lexically and every byte of the path outside `A-Z a-z 0-9 - . _ ~ /` percent-encoded; `init`, `sync`, `update`, `cardinal run`, the launcher and `.github/install_cardinal.sh` must clone that URL, key the cache clone by it and pass it to the `cargo install --git` they run or print, whatever the working directory; the configuration keeps the source as written.
- **SYN-51** (deterministic) When the source declares a format below 5 (SYN-40), `init`, `sync` and `update` must fail with the error `<source> has the format <n>, this cardinal syncs the format 5 and higher` (exit 3, SYN-37) and write nothing, `--dry-run` included.
- **SYN-52** (deterministic) A migration is the file `migrations/<n>.toml` of the source, `<n>` the format it raises the content to: a list `names` of tables `{ old, new }` (a name of the managed content before the format `<n>` and the one that replaced it) and a list `rewrite` of tables `{ path, old, new }` (a text the source seeded in the project file `path` before the format `<n>`, and its replacement), each list optional. `sync` and `update` must apply, in increasing `<n>`, every migration of the source whose `<n>` is greater than the format the project's lock records and not greater than the format of the source; a project without a lock applies none. A migration file that cannot be read or does not have that shape must fail them with an error that names it (exit 3) and write nothing, `--dry-run` included.
- **SYN-53** (deterministic) For each `rewrite` of an applied migration, `sync` and `update` must replace in the project file `path` every occurrence of `old` that starts at the start of a line and ends at the end of a line (or of the file) by `new`, and print `rewritten: <path>` once per file they change; a `path` that is a managed file, the lock, outside the project or missing, and a file that does not hold `old` so, are left untouched without an error. `--dry-run` must print the same lines and write nothing.
- **SYN-54** (deterministic) After the rewrites, `sync` and `update` must print to stderr `warning: <path>:<line> cites <old>, named <new> since the format <n>` for each line of a project-owned file that contains the `old` of a `names` table of an applied migration as a word (no letter, digit nor `_` right before or after it) outside an occurrence of its `new`, once per line and name, `<new>` and `<n>` the name and the format of the last applied migration that renamed it (a later one may rename the `new` of an earlier one), in the order of the paths then of the lines, and must not change the file nor fail because of it. The project-owned files are the files git tracks in the project, other than the managed files, the lock and the files under `issues/done/` or `docs/adr/` (they record the history), that are valid UTF-8; a project that is not a git repository gets no such warning. They judge the files as the run leaves them, and under `--dry-run` as it would.
- **SYN-55** (deterministic) `check` and `sync` must print to stderr `hint: <lock> is of the format <a>, this cardinal reads the format <m>: run `cardinal update` to move the project to a newer revision` once, when the source is a git source (SYN-49; a local directory has no revision to update) and the format the lock records (as the run leaves it for `sync`, as it is under `--dry-run`) is lower than the format the running `cardinal` reads, and must not fail because of it; `update` does not print it.
- **SYN-56** (deterministic) `.github/install_cardinal.sh` must read `source` and `rev` from the `[cardinal]` table of `.claude/cardinal.toml` as a TOML parser does, so that every valid form of the file (a key quoted or in another table, an inline table, a multi-line or escaped string) gives the values `cardinal` reads, a `rev` that is not a string read as none.
- **SYN-57** (deterministic) When `.claude/cardinal.toml` is not valid TOML or its `[cardinal].source` is not a non-empty string, `.github/install_cardinal.sh` must fail (exit 1) with `no source read from .claude/cardinal.toml` on stderr and run no install.
- **SYN-58** (deterministic) When the runner has no `python3` of version 3.11 or later (the first with `tomllib`), `.github/install_cardinal.sh` must fail (exit 1) with an error on stderr that names Python 3.11 and run no install.
- **SYN-59** (deterministic) After `sync` into a git repository, git must ignore `.claude/cardinal.local.toml`, the personal configuration (ADR 0018), which `sync` and `check` never read, write nor report.
- **SYN-60** (deterministic) When the project is the top of a git repository whose `core.hooksPath` is unset and whose source, as the project turns it on (FEA-3), manages no hook of the review gate (SYN-22) and the lock it writes records none (settings it leaves alone, SYN-29, keep the hooks and the gate), `sync` must remove a `pre-commit` of the hooks directory that carries the mark of SYN-18 (up to date, edited or of an older revision), report `removed: native review gate`, and move a `pre-commit.user` back to `pre-commit` reporting `moved: pre-commit.user -> pre-commit`, keeping its content, its mode and, for a symbolic link, the target it reaches; a `pre-commit` without the mark and a `pre-commit.user` with no gate of ours are left untouched; `--dry-run` reports the same and writes nothing. A gate left in place would refuse every commit, no review hook being there to record one.
- **SYN-61** (deterministic) After the report of SYN-16, when `update` wrote the project (not under `--dry-run`, no conflict) and changed a file (`.claude/cardinal.toml` and the lock included; a skip, a conflict or a kept file is no change), and the project has `.claude/skills/commit-message/SKILL.md` as the update leaves it, `update` must print the line `next: commit the update with skill:commit-message` last on stdout. The agent otherwise commits the update with a message written inline, the skill and its checker skipped.

## Scenarios


- (SYN-3) Given a project whose file was never synced but differs from the source, when `sync` runs, then it is a conflict: the file is not ours yet.
- (SYN-6) Given a project whose file already equals the source but is not in the lock, when `sync` runs, then it is locked and reported as unchanged.
- (SYN-11) Given a project already at the resolved commit, when `update` runs, then `rev` is rewritten unchanged, the `sync` reports nothing and the run succeeds.
- (SYN-12) Given a `rev` line with a trailing comment from an earlier update, when `update` runs, then the comment is replaced by the new requested name.
- (SYN-17) Given an abbreviated hash or a name that does not resolve, the fetch by hash is not tried and the error stays "unknown revision".
- (SYN-19) Given a user's `pre-commit` that runs a linter, when `sync` runs, then the linter runs after the gate, and a refusal of the gate stops the commit before it.
- (SYN-19) Given a user's `pre-commit` and a dangling link `pre-commit.user`, when `sync` runs, then it fails changing nothing: the link counts as a `pre-commit.user` that exists.
- (SYN-23) Given a user's `pre-commit` and a dangling link `pre-commit.user`, when `check` runs, then it prints the conflict line, not `missing: native review gate`: the `sync` that fixes a missing gate refuses here.
- (SYN-19, SYN-23) Given a `pre-commit` of the user and a `pre-commit.user` that is a hard link of it (a `sync` killed between the link and the rename), when `check` runs, then it prints `missing: native review gate`, and when `sync` runs, then it installs the gate and `pre-commit.user` keeps the hook of the user.
- (SYN-19) Given a user's `pre-commit` that is a dangling link, when `sync` runs, then the link moves as a link to `pre-commit.user`, the gate is installed and the hooks directory holds no staged file.
- (SYN-24, SYN-25, SYN-26) Given a `.claude/settings.json` that cannot be read or is not valid JSON, then `check` prints one warning saying so instead of one per rule, hook or attribution, whether or not the review hook is managed.
- (SYN-25) Given a hook command that names no file under `.claude/hooks/` (a `just` recipe, a tool on the `PATH`), then it is not reported.
- (SYN-26) Given an `attribution` whose `commit` is empty but whose `pr` is unset, then the warning is printed: Claude Code adds its default text to the pull requests.
- (SYN-27) Given a source that dropped a hook the settings run, when `sync --dry-run` runs, then it warns that the settings run the missing hook, though the file is still there.
- (SYN-27) Given an `update` that applies, then the warnings of its sync come out once, not once for the dry run that precedes it and once for the sync.
- (SYN-22) Given `core.hooksPath` set to a versioned directory, then `sync` leaves it untouched and says the gate is not installed there.
- (SYN-28) Given user settings that exist but cannot be read or are not valid JSON, then the warning is `warning: <user settings> cannot be read or is not valid JSON; Claude Code pauses the cleanup of the transcripts until it is fixed`, not the retention one: the value in force is unknown.
- (SYN-28) Given neither `CLAUDE_CONFIG_DIR` nor `HOME` set (or both empty), then the warning is `warning: the user settings cannot be located (set HOME or CLAUDE_CONFIG_DIR); the retention of the transcripts is not checked`.
- (SYN-29) Given a project whose settings already hold a managed hook in a group with other hooks of its own, when `sync` runs, then nothing is added and the file is not written.
- (SYN-29) Given a project seeded before the rename, whose settings allow `Bash(harness run *)` only, when `sync` runs with a source that manages the allow rule `Bash(cardinal run *)`, then the rule is appended to its `permissions.allow` and `Bash(harness run *)` stays: it is the project's.
- (SYN-29) Given a fragment hook whose matcher matches no group of the project, then it is appended in a new group `{"matcher": ..., "hooks": [hook]}` at the end of its event.
- (SYN-31) Given a source that switches a hook from `rust-script` to a prebuilt binary, when `sync` runs on a project that kept the old declaration unchanged, then the new hook object takes the place of the old one in its group, even when it was alone there, one removal and one addition reported.
- (SYN-33) Given a project that deleted its settings and a source that seeds them, when `sync` seeds them again, then the managed entries are added to the new file without conflict: nothing in it is the project's yet.
- (SYN-38) Given a budget of 1000, a `CLAUDE.md` of 200 bytes, a `.claude/CLAUDE.md` of 900 and an `AGENTS.md` of 2000 that no file imports, then `check` warns that the fixed context is 1100 bytes and that the largest part is `CLAUDE.md` (1100 bytes).
- (SYN-38) Given a budget of 8000 and a work tree whose `CLAUDE.md` is 5000 bytes and imports an `AGENTS.md` of 2500, and skill descriptions 1000, then `check` warns that the fixed context is 8500 bytes and that the largest part is `CLAUDE.md` (5000 bytes); a skill body, loaded on demand, counts for nothing.
- (SYN-40) Given a source that declares the format the running `cardinal` reads, or a lower one, then `sync` goes on as before: a newer `cardinal` reads an older source.
- (SYN-40) Given an `update` to a revision whose format is too new, then the project keeps its `rev` and its files, and the error names the commit of that revision in the install command.
- (SYN-41) Given a lock without a format, then the next `sync` rewrites it with the format of its source.
- (SYN-41) Given a `cardinal` of a higher format syncing a source of a lower one, then the lock records the format of the source: a `cardinal` pinned on that source reads it.
- (SYN-51) Given an `update` to a revision of the format 4, then the project keeps its `rev` and its files.
- (SYN-51) Given a source that declares no format, then it has the format 1 and is refused.
- (SYN-49) Given the source `/x/.git`, then it is cloned; given `../x.git/` (trailing slash) or `/x/X.GIT`, then it is read as a local directory.
- (SYN-50) Given two projects whose source is `../x.git`, each next to a different repository, when `sync` runs in each, then each gets its own repository; given `cardinal run` started from a subdirectory of such a project, then it clones the repository next to the project root.
- (SYN-50) Given the source `git@host:x.git` or `host:x.git`, then it is passed to git as written.
- (SYN-52) Given a project whose lock records no format (1) and a source with `migrations/2.toml` and `migrations/3.toml`, when `update` runs, then both apply, the one of the format 2 first; a later `sync` of the same source applies none.
- (SYN-52) Given a source whose migration names a format not above the one of the lock, then it does not apply: the project already moved past it.
- (SYN-53) Given a justfile line `check: check-old fmt` and the rewrite of the line `check: check-old`, then the line is left as it is: the project changed it.
- (SYN-53) Given an `update` that stops on a conflict (SYN-13), then nothing is rewritten.
- (SYN-53) Given a line ending in `\r\n`, then it ends at the `\r`: the rewrite matches it.
- (SYN-53, SYN-54) Given a `--dry-run` that would remove a managed file or merge the settings, then the removed file is not judged and the settings are judged merged.
- (SYN-54) Given an old name cited twice on one line, then the line is reported once for that name.
- (SYN-54) Given a new name that contains the old one (`check` named `check-all`), then a line that cites only the new one is not reported; nor is `checkout` nor `check_x`, but `check-x` is.
- (SYN-54) Given the format 2 renaming `a` to `b` and the format 3 `b` to `c`, both applied, then a line citing `a` is named `c` since the format 3.
- (SYN-54) Given a file that git does not track, or a file that is not valid UTF-8, then it is not read.
- (SYN-55) Given a `sync` that moves the lock to the format the `cardinal` reads, then no hint is printed.
- (SYN-56) Given a `source` key in a table before `[cardinal]`, when the installer runs, then it installs from `[cardinal].source`, as `cardinal` does.
- (SYN-56) Given a `rev` that is not a string, when the installer runs, then it installs with no `rev`, as `cardinal` reads none.
- (SYN-57) Given a `source = ""` or a `source = 1`, when the installer runs, then it fails with the no-source error.
- (SYN-60) Given a gate installed with a user's `pre-commit` chained, when the project turns the feature `review-gate` off and runs `sync`, then the user's hook is `pre-commit` again and a commit runs it; a second `sync` reports nothing about the gate.
- (SYN-60) Given a `.claude/settings.json` that is not valid JSON, when the source no longer manages the gate, then `sync` leaves the gate: the lock still records its hooks.
- (SYN-60) Given `core.hooksPath` set, when the source no longer manages the gate, then `sync` touches no hook, the one under `.git/hooks` included.
- (SYN-61) Given an update that moves the revision, when it is written, then its output ends with the `next:` line; under `--dry-run`, at the same revision with nothing changed (a skipped gate included), or for a project without the skill, it does not.

## Non-goals

- The worktrees of one repository share its hooks directory (SYN-21): a `sync` in one of them installs or removes
  the gate for all, as its own `.claude/cardinal.toml` says.
- Installing the gate under a `core.hooksPath` the project sets itself.
- Merging a local change with a source change: a drifted file is fixed in the central repository.
- Fetching more than a branch, tag or commit of a git source.
- Making `check` depend on the source: it compares the project with its lock only, so the pin cannot break it.
- Rewriting the user settings: `cardinal` warns of the retention, the user raises it.
- Reading the managed settings of an organisation, which can override the retention.
- Guaranteeing that a host serves an unreferenced commit: it depends on the host.
- Managing the keys of the settings other than `permissions.allow`, `permissions.ask`, `permissions.deny` and `hooks` (the attribution stays a warning, SYN-26).
- A separate settings file read by Claude Code: it reads one shared file per project (`.claude/settings.json`) besides the personal `settings.local.json`.
- Refusing a source of the format 5 or higher but lower than the running `cardinal`'s: each format reads the ones before it, down to 5.
- Telling whether a change of the managed content needed a new format: the ADR 0014 rule says when to raise it, a review checks it.
- Making a `cardinal` released before SYN-40 refuse anything: it cannot be changed.
- Reading or migrating a project of the old names (`.claude/harness.toml`, `.claude/harness.lock`, `harness.just`): the `cardinal` of its revision does (ADR 0016).
- Rewriting a cited old name in a project-owned file: the warning gives its line, the agent or the user edits it.
- Rewriting the `source` URL of a renamed repository: the forge redirects the old one, and telling a redirect needs the network.
- Telling a project of the names before a migration that renames the configuration or the lock itself: the migration that renames them brings its own detection, as ADR 0016 left it.
